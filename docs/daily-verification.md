# 일일 재료 상점 검증 — 아직 적용 불가

> 아래는 단계별 조사 기록입니다. 현재 배포 상태는 README를 참고하세요.

## 2026-09-24 실게임 미진열 제보 추가 조사

설치된 DB의 예약 범위에 재료 상품 106행이 존재하지만, 읽기 전용으로 확인한 세이브의
`automaticshop_buyable_goods_ids`에는 기존 4개 상품만 남아 있었다. DB 설치 실패와
실제 판매 목록 생성 실패를 구분해야 한다. 아직 다음 날짜에 해결된다는 검증은 없다.

`dev/audit-daily-date-refs.py` 및 `dev/audit-daily-shop.py`로 날짜 비교 전역값의
쓰기 경로를 추적했다. `0x1324d80`은 로그인 횟수 성격의 카운터 갱신과 함께 날짜를 쓰며,
일일 검사 `0x12d8f70`의 날짜 불일치 분기에서 `0x12d02d0`을 통해 호출된다.
관찰한 직접 호출 경로만으로 로그인 직후 갱신이 무조건 누락된다고 결론 내릴 수 없다.
전용 `automaticshop_daily_date` 저장 필드는 확인되지 않았으므로 이를 가정하면 안 된다.

현재 선정 후크는 초기화가 호출됐을 때만 동작한다. 이미 만들어진 목록에 대한 최초
재료 추가 경로는 미구현이며, 이를 해결하려고 공용 초기화를 강제 호출하면 기존 상품의
구매 이력도 초기화할 수 있다. 이 우회는 적용하지 않았다. 게임과 세이브는 변경하지 않았다.

검증일: 2026-09-24. Steam 빌드 25386710의 로컬 EXE를 읽기 전용으로 사용했다.
SHA-256: `b29bf446786aed3c6c47b69e112e4ba6d1e97ed6b7ead791c80754472432ef6a`.

## 실제로 실행한 검증

`dev/test-native-selection.py`는 실제 실행 파일의 선정 루프를 에뮬레이션한다.
DB 조회·셔플 이후의 합성 행을 입력하고, 후보 맵 삽입 호출만 대체한다.
고정 8개 / 고정 5개 제한 / 랜덤 8개 / 혼합 후보의 4개 케이스가 통과했다.
랜덤 후보는 높은 가중치를 주어도 출력되지 않는다.

`dev/test-native-daily.py`는 실제 날짜 비교·갱신 결정·호출자 분기를 실행한다.
날짜 변환 결과와 시계 입력은 합성 값이고 전체 상점 초기화 호출은 기록만 한다.

| 날짜 입력 | 공용 초기화 호출 수 |
|---|---:|
| 저장 날짜와 같은 날짜 | 0 |
| 다음 날 | 1 |
| 7일 후 | 1 |
| 저장 날짜보다 이전 날짜 | 1 |
| 저장 날짜 0, 현재 날짜 있음 | 1 |

같은 스크립트에서 요일 상품 설정 함수와 리사이클 설정 함수의 앞부분도 실행했다.
두 함수가 각자의 상품 목록 관련 버퍼 두 개를 비우는 것을 확인했다.
할당자 호출은 대체했으며 대상 이외 객체 바이트가 유지되는지 함께 검사했다.
이는 **구매 이력이 보존된다는 검증이 아니다**. 버퍼의 저장 필드 대응 및
전체 초기화 완료 후 상태는 별도 확인해야 한다.

## 결론과 적용 차단 이유

- 일일 비교 경로는 남아 있다. 단순히 시간이 앞으로 흐른 경우뿐 아니라
  날짜가 다르기만 해도 갱신 대상이 된다.
- 공용 초기화 함수는 COMMON, RE, 요일 그룹을 모두 처리한다.
  재료만 갱신하려고 이 함수를 임의 호출하는 구현은 채택하지 않는다.
- AP 상품 추가만으로는 현재 선정 코드에서 랜덤 진열이 되지 않는다.
- 11개 격리 테스트의 통과는 모드 완성 또는 실게임 구매 성공을 뜻하지 않는다.

## 아직 검증되지 않은 필수 항목

후속 [구매 연결 검증](purchase-verification.md)에서 결제·지급·stock=1 목록 제거의
네이티브 호출 연결을 확인했다. 아래 항목의 실제 서비스·저장·UI 통합 검증은 남아 있다.

1. 유료 구매 시 킬코인 차감과 재료 5개 지급이 정확히 한 번 발생하는지.
2. 품절 판정에 stock / pack_count / 구매 상품 ID가 각각 어떻게 사용되는지.
3. 메뉴 재진입·저장·재접속 뒤에도 그날의 목록과 구매 이력이 유지되는지.
4. 날짜 변경 시 재료만 새로 선정하고 재고가 복구되는지.
5. 기존 COMMON·블러드늄·리사이클 상품과 구매 이력이 보존되는지.
6. 날짜 경계의 실제 시각대 및 게임 실행 중 갱신 호출 시점.

적용용 패치는 아직 없으며 게임 EXE·UPK·DB·세이브는 변경하지 않았다.
이 조사 시점에는 2번 데칼 및 3번 탄약 기능을 시작하지 않았다.
이후 진행 상황은 [현재 README](../README.md)를 참고한다.

## 후속 구현 — 기존 일일 초기화에 합류

사용자와 방향을 확정했다. 공용 초기화를 추가 호출하지 않고, 원래 일일 초기화의
COMMON 선정 과정에 재료 선정을 합류시킨다. RE·요일 그룹의 원래 초기화는 유지한다.
위의 구매 이력 보존 조건은 '원래 날짜 변경 처리 대비 추가 변경이 없어야 한다'는 뜻이다.

- `src/material-selector.js`: 기존 고정 상품과 일반 후보 분기는 유지하고,
  예약 ID의 재료 후보만 기본 7종 추가하는 네이티브 게이트를 생성한다.
  게임 설치용 코드 공간 확보·후크 배치는 아직 구현하지 않았다.
- 격리 메모리에 게이트를 넣은 실제 루프 테스트 12개 통과. 기존 4개 사례와
  재료 개수 제한, 제한 전후 고정 상품 보존, 후보 부족, ID 경계, 잘못된 유형,
  역순 후보, 타 상품 후보 혼합, 빈 목록을 검사했다.
- 후보 순서가 바뀌면 선정도 달라짐을 검증했으나 실제 게임 셔플의 분포는 미검증이다.
- `src/material-catalog.js`: DB를 바꾸지 않는 상품 생성 계획. 현재 DB 재료 106종을
  읽고 COMMON 후보, stock=1, pack_count=5로 계획한다. 이 조합이 실제로 하루 한 묶음
  판매를 의미하는지는 아직 구매 경로 검증이 필요하다.
- 사용자가 희귀도별 고정 가격을 선택했다. `material-prices.json`은 5개 묶음 가격이며
  기본값은 ★1~8 순서로 10,000 / 15,000 / 20,000 / 25,000 / 50,000 / 75,000 /
  100,000 / 125,000 킬코인이다. 로컬 DB 일반 재료 ALUMI 계열의 개당 구매가 ×5를
  기준으로 한 초안이며, 같은 희귀도는 같은 가격을 사용한다.
- Node 테스트 5개 통과. 실제 DB 조회는 readOnly로 수행했다.

아직 배포용 패치나 실게임 구매 검증 완료 상태는 아니다. 예약 ID 범위의 게임 내
직렬화 적합성, DB 로딩과 전체 선정·결제·품절·재접속 통합 검증이 남아 있다.
